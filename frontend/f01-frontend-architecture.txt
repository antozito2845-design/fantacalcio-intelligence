F01 - FRONTEND ARCHITECTURE DECISION
Data: 2026-08-22

1. DECISIONE

RACCOMANDAZIONE UNICA: React + TypeScript + Vite, come Single Page Application
separata dal backend Spring Boot.

La decisione e adeguata a una web application autenticata, data-intensive e molto
interattiva, con dashboard, tabelle, filtri, aste live e workflow applicativi. Il
prodotto non presenta oggi un requisito SEO sostanziale sulle schermate principali;
SSR, React Server Components e un server Node applicativo aggiungerebbero complessita
operativa senza vantaggio proporzionato. Vite offre bootstrap/build rapido, asset
statici distribuibili via CDN/reverse proxy e integrazione diretta con API separate.

2. VALUTAZIONE DELLE OPZIONI

React + TypeScript + Vite - SCELTA
- Ottimo per UI altamente interattive e feature modulari.
- Deployment statico semplice; API Spring Boot restano autorevoli e separate.
- Ecosistema maturo per query caching, tabelle, form, grafici, accessibilita e test.
- TypeScript strict limita drift e difetti sui DTO.
- PWA futura possibile tramite plugin dedicato, solo quando richiesta.
- Portfolio professionale forte senza imporre infrastruttura server frontend.

Next.js + TypeScript - NON SCELTO
- Valido se marketing SEO, SSR, streaming server-side o BFF Node fossero requisiti
  centrali. Oggi l'app core e privata/interattiva e il backend e gia separato.
- Introduce doppia superficie server/deployment, cache e confini server/client da
  governare. Potrebbe essere rivalutato solo per un sito marketing separato o un BFF
  auth deliberato, non come default dell'app operativa.

Angular + TypeScript - NON SCELTO
- Offre struttura, DI, router e form integrati, ed e adatto a team enterprise.
- Per questo prodotto greenfield aumenta peso concettuale e boilerplate senza un
  requisito organizzativo che lo giustifichi. React con regole architetturali chiare
  mantiene modularita e velocita evolutiva superiori per il team/progetto attuale.

Il frontend iniziale e vuoto: non esiste costo di migrazione o lock-in preesistente.

3. STACK PROPOSTO (DA INSTALLARE SOLO IN F02 AUTORIZZATO)

Core:
- React, TypeScript strict, Vite.
- React Router per routing dichiarativo e lazy loading per area funzionale.

Dati e stato:
- fetch wrapper tipizzato come client HTTP centralizzato; nessun Axios finche fetch
  soddisfa timeout, abort, header e parsing richiesti.
- TanStack Query per server state, cache, deduplica, invalidazione e retry controllato.
- Zustand solo per stato client realmente trasversale e complesso (es. live auction);
  Context/useState per sessione e preferenze semplici. Nessun global store universale.
- Zod alle boundary esterne critiche e per variabili ambiente; evitare validazione
  duplicata indiscriminata di ogni payload.

Form e UI:
- React Hook Form con resolver Zod per form non banali.
- CSS Modules + custom properties/tokens globali per styling isolato e tema coerente.
- Radix UI primitives non stilizzate, adottate selettivamente per dialog, menu,
  tooltip, popover e tabs accessibili. Nessuna suite UI monolitica.
- Lucide React per un sistema icone coerente; icone sempre accompagnate da label o
  accessible name quando interattive.

Qualita:
- Vitest + React Testing Library + user-event + MSW per unit/component/integration.
- Playwright per pochi flussi E2E ad alto valore.
- ESLint con regole TypeScript/React Hooks/accessibility; Prettier.
- axe (in test mirati), semantic HTML, keyboard navigation, focus management,
  contrast checks e reduced-motion.
- TanStack Table solo quando le griglie complesse lo richiederanno.
- Libreria chart scelta in F03 sul caso reale; non installarla nello scaffold base.

Regole di dipendenza:
- app compone provider e router; non contiene logica di dominio.
- features possiedono UI, query, adapter e logica del proprio dominio.
- components e realmente condiviso e non importa features.
- api/client gestisce trasporto; api/contracts descrive boundary; domain contiene
  modelli semantici stabili. Adapter feature-specific impediscono ai DTO di invadere UI.
- pages compongono feature e layout; non diventano contenitori di business logic.
- import alias unico @/ verso src; barrel file solo dove migliorano davvero l'API.
- test colocati vicino al codice; src/test contiene setup, fixture builders e MSW.

5. STRATEGIA FRONTEND/BACKEND

Development:
- Variabile VITE_API_BASE_URL, validata all'avvio.
- Valore diretto ammesso: http://localhost:8080/api/v1.
- Strategia preferita in sviluppo: proxy Vite /api -> http://localhost:8080 e base
  relativa /api/v1, riducendo differenze same-origin e mantenendo il target configurabile.

Production:
- Preferire reverse proxy/gateway same-origin: app su https://prodotto.example e API
  su /api/v1. In alternativa origin API separata esplicita in configurazione deploy e
  allowlist CORS backend corrispondente. Mai hardcodare host nei componenti.
- Le variabili VITE_* sono pubbliche nel bundle: nessun segreto o credenziale al loro interno.

Client HTTP:
- Un solo client centralizzato basato su fetch, URL normalizzati, JSON parsing sicuro,
  Accept/Content-Type coerenti e AbortController.
- Timeout iniziale proposto: 10 s per letture ordinarie, 20-30 s solo per operazioni
  esplicitamente lunghe; valori configurati per classe di richiesta, non sparsi.
- Request ID/telemetria solo se il backend espone un contratto utile in futuro.
- Adapter converte ApiErrorResponse in AppError tipizzato preservando status, message,
  path e timestamp; fallback robusto per body vuoti/non JSON (specie 401/403/502).

Auth:
- HTTP Basic e il contratto corrente. Header Authorization prodotto centralmente.
- Credenziali mantenute esclusivamente in memoria per la sessione UI, mai in URL,
  log, localStorage o sessionStorage. Il refresh della pagina richiede nuova login.
- Route guard e capability UI migliorano UX ma non sostituiscono l'autorizzazione backend.
- Prima di una produzione commerciale e raccomandata una decisione autorizzata su
  auth moderna/BFF-cookie HttpOnly; non e una modifica F01.

Gestione status:
- 400/422: errore di input; associare ai campi solo se esiste dettaglio strutturato,
  altrimenti messaggio form-level. Oggi il backend emette principalmente 400.
- 401: azzerare credenziali in memoria, aprire flusso login, non fare retry automatico.
- 403: mostrare accesso negato mantenendo la sessione.
- 404: empty/not-found contestuale, non toast generico.
- 409: conflitto di stato; mostrare azione di refresh/reconcile e invalidare query utile.
- 429: rispettare Retry-After se presente; niente loop di retry/polling.
- 500/rete: messaggio sicuro con retry manuale; mai mostrare stack o dettagli sensibili.

Loading/retry:
- Skeleton per primo caricamento strutturale, progress per mutazioni, background refresh
  discreto e stato empty distinto dall'errore.
- Query idempotenti: massimo 1-2 retry con exponential backoff e jitter solo per rete/5xx.
- Nessun retry per 400/401/403/404/409/422. Mutazioni mai ritentate automaticamente
  senza idempotenza esplicita. Polling live adattivo e sospeso su tab non visibile.

6. DIREZIONE VISIVA

Posizionamento: SaaS sportivo/data intelligence premium, editoriale e operativo,
non clone di portali fantacalcio e non admin template generico.

- Densita: media-alta su desktop per confronto dati, con gerarchia forte e progressive
  disclosure; touch target e respiro maggiori su tablet/mobile.
- Tipografia: sans contemporanea molto leggibile, numeri tabulari per prezzo/statistiche,
  scala contenuta e pesi usati per gerarchia, non decorazione.
- Card: superfici sobrie per insight/comandi, evitando mosaici uniformi senza priorita.
- Tabelle: sticky header, colonne prioritarie, sorting/filtering accessibile e modalita
  card/summary su mobile; niente scroll orizzontale incontrollato.
- Chart: poche visualizzazioni decisionali, palette semantica accessibile, tooltip anche
  da tastiera e alternativa tabellare/testuale.
- Priorita: desktop-first per auction intelligence e confronto; mobile-first nei flussi
  rapidi live, lineup e consultazione. Responsive progettato per task, non per semplice shrink.
- Tema: dark come modalita premium ottimizzata per live auction, light pienamente supportata;
  seguire prefers-color-scheme e scelta utente. Token semantici rendono i temi equivalenti.
- Ruoli P/D/C/A: abbreviazione + nome/tooltip, forma o icona e token semantico; il colore
  non e mai l'unico discriminante.
- Difficulty easy/medium/hard: label testuale + scala/marker ordinato, colore secondario.
- Confidence/score: percentuale o livello con spiegazione, intervallo e data freshness;
  evitare precisione visiva ingannevole.
- Auction price/range: valore consigliato dominante, min-max visibile, indicatore rispetto
  a budget/quotazione e motivazione; numeri tabulari e unita sempre esplicite.
- Accessibilita: WCAG 2.2 AA come baseline, focus visibile, contrasto, tastiera completa,
  screen reader semantics, motion ridotta e messaggi live non invasivi.

I colori finali, il font concreto e la libreria chart saranno decisi con evidenza visuale
in un blocco design dedicato, non in F01.

7. RISCHI E GATE F02

Gate obbligatori prima dello scaffold:
1. Ripristinare npm/npx e registrarne versioni/esito in evidenza.
2. Fissare Node supportato e package manager/lockfile unico.
3. Confermare strategia dev proxy e VITE_API_BASE_URL.
4. Creare foundation minimale con strict TypeScript, lint, test e directory base.
5. Eseguire una contract probe controllata su API reali quando il backend sara avviato.

Rischi aperti:
- Basic Auth commerciale e persistenza sessione richiedono decisione futura.
- Assenza OpenAPI aumenta manutenzione tipi.
- Formato security error e 429 da certificare.
- CORS di produzione deve coincidere esattamente con il dominio deploy.
- Nessun endpoint va dichiarato mancante senza una user-story/contract matrix F02-F03;
  la mappa attuale appare ampia, ma DTO e granularita devono essere verificati per feature.

8. ESITO

L'architettura e definita, proporzionata e pronta per una foundation F02 controllata.
Nessuna funzionalita applicativa e stata implementata e nessuna dipendenza installata.
